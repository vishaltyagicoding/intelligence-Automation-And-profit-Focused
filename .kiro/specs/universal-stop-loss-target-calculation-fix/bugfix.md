# Bugfix Requirements Document

## Introduction

The SmartRisk platform has critical defects in stop loss and target price calculations across all cryptocurrency symbols (BTCUSD, LTCUSD, XAUUSD, ETHUSD). The current implementation uses a naive percentage-based approach (2% stop loss, 4% target) that fails to account for:

1. **Symbol price level differences**: High-priced symbols like XAUUSD ($4,500+) and BTCUSD ($100,000+) require absolute point-based buffers, while low-priced symbols like ETHUSD ($3,000) and LTCUSD ($100) need percentage-based buffers.

2. **Market structure analysis**: The system ignores actual candle patterns (bearish/bullish candles) when setting stop loss levels, resulting in stops that are either too tight (triggering prematurely) or identical to entry prices (zero risk protection).

3. **Data inconsistency**: Email alerts calculate values differently than the history page, and the history API may be using cached/stale data instead of reading directly from the database.

4. **ATR-based validation**: No volatility-based safety guards exist to prevent stops that are unrealistically tight or wide relative to market conditions.

This bug affects all trading signals generated by the platform, making them unusable for actual trading. The fix requires implementing a universal calculation system that adapts to symbol characteristics and market structure while ensuring data consistency across all display channels (history page, email alerts, WebSocket broadcasts).

**Impact**: All historical signals show incorrect stop loss and target values. Users cannot trust the platform for real trading decisions.

**Affected Components**:
- `trading/views.py` (get_signal_history API endpoint)
- `trading/consumers.py` (WebSocket signal broadcasting and email alerts)
- `reversal_zones/reversal_calculator.py` (signal generation logic)
- Database: `ReversalZone` model (stores incorrect SL/TP values)

## Bug Analysis

### Current Behavior (Defect)

1.1 WHEN a signal is generated for high-priced symbols (XAUUSD at $4,569.30, BTCUSD at $100,000+) THEN the system calculates stop_loss = outer_bottom and target = outer_top using a fixed 2% and 4% percentage, resulting in entry = stop_loss = target (all identical values) or impossibly tight stops (Risk = $0.01 to $0.28).

1.2 WHEN a signal is generated for any symbol THEN the system does not scan historical candles to find the last bearish/bullish candle for stop loss placement, instead using arbitrary percentage offsets that ignore market structure.

1.3 WHEN a signal is generated THEN the system does not apply ATR-based safety guards, allowing stop loss distances that are either too tight (< 1.5 × ATR) or too wide (> 3.0 × ATR) relative to market volatility.

1.4 WHEN the history API endpoint (`/api/trading/signal-history/<symbol>/`) is called THEN the system reads stop_loss and target values directly from the database without recalculation, but these stored values were calculated using the broken percentage-based logic.

1.5 WHEN email alerts are sent via `trading/consumers.py` THEN the system calculates `email_stop_loss = outer_bot if is_bull else outer_top` and `email_target = outer_top if is_bull else outer_bot` using the same broken percentage-based outer_top/outer_bottom values, resulting in email alerts showing different (but equally incorrect) values than the history page.

1.6 WHEN duplicate signals exist in the database for the same symbol and timestamp with different SL/TP values THEN the system does not detect or resolve these data inconsistencies, causing the history page to display conflicting information.

1.7 WHEN the target price is calculated THEN the system uses a fixed 4% offset (target = entry × 1.04 for BUY) instead of a 2:1 risk-reward ratio based on the actual stop loss distance.

1.8 WHEN low-priced symbols (ETHUSD ≤ $1000, LTCUSD ≤ $1000) generate signals THEN the system applies the same percentage-based logic as high-priced symbols, but the calculations are inconsistent and produce different errors (duplicate entries with varying SL/TP values).

### Expected Behavior (Correct)

2.1 WHEN a signal is generated for high-priced symbols (price > $1000) THEN the system SHALL scan backwards to find the first bearish candle (for BUY signals) or bullish candle (for SELL signals), measure the candle's move in absolute points, apply a buffer using absolute points (20 real points = $20), and set stop_loss = candle_low - buffer (for BUY) or candle_high + buffer (for SELL).

2.2 WHEN a signal is generated for low-priced symbols (price ≤ $1000) THEN the system SHALL scan backwards to find the first bearish/bullish candle, measure the candle's move as a percentage of entry price, apply a buffer using percentage (0.03% of entry price), and set stop_loss accordingly.

2.3 WHEN a stop loss distance is calculated THEN the system SHALL apply ATR(14) safety guards: if calculated SL distance < 1.5 × ATR, expand to 1.5 × ATR; if calculated SL distance > 3.0 × ATR, contract to 3.0 × ATR.

2.4 WHEN a target price is calculated THEN the system SHALL use a 2:1 risk-reward ratio: Risk = |entry - stop_loss|, BUY target = entry + (2 × Risk), SELL target = entry - (2 × Risk).

2.5 WHEN a new signal is generated and saved to the database THEN the system SHALL calculate stop_loss and target inline before saving, ensuring the ReversalZone record contains correct values from the moment of creation.

2.6 WHEN the history API endpoint is called THEN the system SHALL read stop_loss and target values directly from the database without caching, ensuring real-time consistency with the stored data.

2.7 WHEN email alerts are sent THEN the system SHALL read stop_loss and target values from the saved ReversalZone record (not recalculate them), ensuring email alerts display identical values to the history page.

2.8 WHEN all prices are calculated or displayed THEN the system SHALL round all values to 2 decimal places for consistency across all channels (database, API, email, WebSocket).

2.9 WHEN scanning backwards for bearish/bullish candles THEN the system SHALL skip doji candles (candles where |close - open| < 0.01% of price) to find meaningful price moves.

2.10 WHEN applying buffer logic for high-priced symbols THEN the system SHALL use: if 20 ≤ move ≤ 30 → buffer = move + 20; else if move < 20 → buffer = move + 20; else buffer = move.

2.11 WHEN applying buffer logic for low-priced symbols THEN the system SHALL use: move_pct = move / entry; if 0.0002 ≤ move_pct ≤ 0.0005 → buffer = move + (entry × 0.0003); else if move_pct < 0.0002 → buffer = move + (entry × 0.0003); else buffer = move.

2.12 WHEN a Django management command `recalculate_historical_signals` is executed THEN the system SHALL iterate through all ReversalZone records, recalculate stop_loss and target using the new universal logic, and update the database records.

### Unchanged Behavior (Regression Prevention)

3.1 WHEN a signal is generated and passes the anti-chop filter (1-hour minimum gap, strict alternation BUY→SELL→BUY) THEN the system SHALL CONTINUE TO enforce these filters and save the signal to the ReversalZone table.

3.2 WHEN the history API applies time-distance filtering (1-hour minimum gap between signals) THEN the system SHALL CONTINUE TO apply this filter to the returned signal list.

3.3 WHEN a signal is broadcast via WebSocket THEN the system SHALL CONTINUE TO check alternation with the last DB signal and block consecutive signals of the same type.

3.4 WHEN email alerts are sent to paid subscribers THEN the system SHALL CONTINUE TO filter recipients based on subscription status and symbol/timeframe preferences.

3.5 WHEN the reversal zone calculator generates zones THEN the system SHALL CONTINUE TO calculate center_price, outer_top, outer_bottom, core_top, core_bottom, is_bullish, and label_text as before (only stop_loss and target calculation logic changes).

3.6 WHEN the frontend requests signal history via `/api/trading/signal-history/<symbol>/?timeframe=15m` THEN the system SHALL CONTINUE TO return the same JSON structure with fields: bar_index, is_bullish, center_price, stop_loss, target, outer_top, outer_bottom, core_top, core_bottom, label, timestamp.

3.7 WHEN the system maps frontend symbols to Binance symbols THEN the system SHALL CONTINUE TO use the existing mapping: XAUUSD → PAXGUSDT, BTCUSD → BTCUSDT, ETHUSD → ETHUSDT, LTCUSD → LTCUSDT.

3.8 WHEN historical candle data is fetched for stop loss calculation THEN the system SHALL CONTINUE TO use Binance.US API (`https://api.binance.us/api/v3/klines`) as the data source.

3.9 WHEN signals are displayed on the frontend chart THEN the system SHALL CONTINUE TO show the same visual elements (reversal zones, labels, colors) with only the stop_loss and target values updated.

3.10 WHEN the database constraint blocks consecutive signals of the same type THEN the system SHALL CONTINUE TO log this as an INFO message (not an error) and prevent the duplicate signal from being saved.
